## EXP-DLG-001 LLM NPC 대화 품질 기준 측정

- 날짜: 2026-10-11 · 데이터: `evals/dialogue-cases.jsonl` 21개 케이스, NPC 응답 78개
- 결과 파일: `20261011-0620-dialogue-baseline.json`

**문제.** LLM이 NPC 대사를 만들 때 장면을 벗어나거나 메뉴에 없는 품목을 말하는지, 응답 시간이 대화에 쓸 만한지 확인해야 한다.

**기준 성능.**

| 지표 | 값 |
|---|---|
| 장면 이탈률 (첫 응답이 가드에 걸림) | 5.1% |
| 메뉴 환각률 | 0% |
| 재생성률 / 템플릿 대체율 | 5.1% / 2.6% |
| 최종 응답 가드 통과율 | 100% |
| Director 행동 정확도 | 100% |
| LLM 응답 시간 평균 / p50 / p95 | 632 / 552 / 1026 ms |

**원인 분석.** 가드에 걸린 첫 응답 4건은 모두 "3문장 이상"이었다. 메뉴 환각은 없었다. Director가 행동을 정하고 LLM은 표현만 하는 구조라서 LLM이 메뉴를 지어낼 여지가 작았다.

**결과 및 다음 실험.** 응답 시간 p95 1.03초는 설계의 LLM 예산(1.2초) 안에 있다. 문장 수 위반은 재생성이나 템플릿으로 모두 걸러졌다. 단계 3에서 STT·TTS를 붙인 뒤 전체 턴 지연(목표 3초)을 다시 잰다.

**재측정 (가드 규칙 추가 후)** (`20261011-0638-dialogue-after-fixes.json`)

스모크 테스트에서 주문이 끝났는데 NPC가 "Is that everything?"이라고 다시 묻는 문제를 발견했다. 그래서 장면이 끝나는 행동(close, acknowledge_cancel, end_unfinished)에서는 질문을 금지하는 규칙을 가드에 추가했다.

| 지표 | 기준 | 재측정 |
|---|---|---|
| 장면 이탈률 | 5.1% (문장 수 4) | 6.4% (문장 수 4 + 종료 후 질문 1) |
| 메뉴 환각률 | 0% | 0% |
| 템플릿 대체율 | 2.6% | 3.8% |
| 최종 응답 가드 통과율 | 100% | 100% |
| LLM 응답 시간 p50 / p95 | 552 / 1026 ms | 536 / 1233 ms |

이탈률이 오른 것은 기준이 엄격해졌기 때문이다(새 규칙이 1건을 잡음). p95가 LLM 예산 1.2초를 조금 넘었다. 재생성이 일어난 턴이 p95를 끌어올리므로, 다음에는 문장 수 위반을 줄이는 방법(예: `max_tokens`를 줄이거나 문장 수를 세는 대신 마지막 두 문장만 쓰기)을 실험한다.

참고: 실행 전 실제 대화 점검에서 가드가 "We **only serve** cold brew iced"를 메뉴 외 품목("only serve cold brew")으로 잘못 막는 문제를 발견했다. 흔한 동사·부사를 불용어에 추가해 고쳤다(`tests/test_guard.py`).

**재측정 2 (NPC 검증 보강 후, D-025)** (`20261011-1244-dialogue-dialogue-npc-checks-port.json`)

문제: 가드는 메뉴·금지어·문장 수만 본다. 주문을 다시 말하는 대사가 실제 주문과 달라도(상태 표류), 바리스타가 손님처럼 "can I get a latte?"라고 말해도 통과한다. 또 재생성 요청이 위반 이름만 나열하고 temperature가 같아서, 별도 실험에서는 재생성한 대사가 첫 대사와 똑같이 나왔다.

개선: 주문 복창 상태 검사, 역할 혼동 금지 패턴, 위반별 구체적 재생성 지시 + 재생성 temperature 0.9. 거부된 첫 대사도 결과에 남기도록 평가 스크립트를 고쳤다(가드가 맞게 거부했는지 사람이 확인할 수 있게).

| 지표 | 재측정 1 | 재측정 2 |
|---|---|---|
| 장면 이탈률 (첫 응답 거부) | 6.4% | 9.0% |
| 메뉴 환각률 | 0% | 0% |
| 템플릿 대체율 | 3.8% | 5.1% |
| 최종 응답 가드 통과율 | 100% | 100% |
| Director 행동 정확도 | 100% | 100% |
| LLM 응답 시간 p50 / p95 | 536 / 1233 ms | 448 / 888 ms |

거부 사유를 다시 확인하려고 거부가 나온 7개 케이스만 다시 돌려 첫 대사를 읽었다(`20261011-1245-dialogue-probe.json`). 거부 4건이 모두 맞는 거부였다.

- 문장 수 2건: "Got it! What size would you like? Small, medium, or large?" (3문장)
- 종료 후 질문 1건: 주문 종료 대사에서 "What would you like to order?"
- **주문 복창 불일치 1건: "Your medium iced Americano with oat milk."** — 손님은 우유 없이 주문했다(Americano는 우유 불가). 이전 가드라면 그대로 손님에게 나갔을 대사다.

결과: 이탈률·대체율이 오른 것은 새 검사가 실제 오류를 더 잡았기 때문이다. p95는 이번 실행에서 예산(1.2초) 안이었지만 실행마다 흔들린다(재측정 1은 1233 ms). 실행 1회, 78개 응답 기준이다.

다음 실험: 문장 수 위반이 여전히 가장 많다. 지시문을 "질문 하나에 선택지를 넣어라"처럼 문장 구조로 바꾸는 방법과, `extracted` 없이 `reply`만 받는 현재 스키마에서 `max_tokens`를 줄이는 방법을 비교한다. 가드가 못 잡는 어색한 대사(자연스러움)는 사람 평가로 따로 잰다.

## EXP-FB-001 Learning Evaluator 문법 오류 탐지

- 날짜: 2026-10-11 · 데이터: `evals/feedback-cases.jsonl` 10개 (오류 있는 대화 7, 없는 대화 3)
- 채점: 발화 단위. 예측한 문법 오류가 정답과 같은 고객 발화를 가리키면 TP.

**문제.** 피드백이 실제 실수를 찾아내는지, 맞게 말한 것을 틀렸다고 하지 않는지 측정한다.

**기준 성능** (`20261011-0621-feedback-baseline.json`)

| precision | recall | F1 | 잘못된 지적 비율 | 오류 없는 대화에 지적 |
|---|---|---|---|---|
| 1.000 | 0.286 | 0.444 | 0% | 0/3 |

**원인 분석.** 놓친 5건 중 4건은 모델이 문법 오류를 `unnatural_expressions`(어색한 표현)로 분류했다. 예: "Can I **has** a cold brew?", "I would like **an** latte". 또 "Hot.", "Medium." 같은 정상적인 짧은 답을 어색하다고 지적했다. 프롬프트의 "실제 실수만 보고하라"는 문장과 두 분류의 경계가 모호했던 것이 원인이다.

**개선 1: 프롬프트 v2.** 두 단계 판단 규칙을 넣었다. 먼저 "선생님이 틀렸다고 표시할까?"를 보고 맞으면 문법 오류로 분류하고, 문법이 맞는 문장만 자연스러움을 본다. 오류 유형별 예시와 "짧은 답은 지적 금지" 목록도 넣었다.

**재측정** (`20261011-0623-feedback-prompt-v2.json`)

| precision | recall | F1 | 잘못된 지적 비율 | 오류 없는 대화에 지적 |
|---|---|---|---|---|
| 0.833 | 0.714 | **0.769** | 16.7% | 0/3 |

문법 탐지는 크게 나아졌지만 짧은 답에 대한 "어색한 표현" 지적이 5건 남았다("Hot.", "Medium.", "Hot please." 등). 8B 모델이 금지 목록을 다 지키지 못했다.

**개선 2: 짧은 답 필터 (코드).** 장면 어휘(메뉴 별칭, 의도 표현)와 불용어로만 이루어진 3단어 이하 발화는 지적 대상에서 뺀다. 수량 단어는 제외해서 "Two latte."는 계속 잡힌다.

**재측정** (`20261011-0625-feedback-prompt-v2-shortfilter.json`)

| precision | recall | F1 | 잘못된 지적 비율 | 짧은 답에 대한 어색한 표현 지적 |
|---|---|---|---|---|
| 0.833 | 0.714 | 0.769 | 16.7% | 5건 → **0건** |

남은 오탐 1건은 "Medium size please."에 관사가 빠졌다는 지적으로, 사람 라벨러 사이에서도 의견이 갈릴 수 있는 경우다. 남은 미탐 2건은 "two latte"(복수형)와 "Give me hot chocolate."(관사, 모델은 어색한 표현으로만 분류)이다.

**회귀 발견.** 스모크 테스트에서 피드백 요약이 프롬프트의 예시 문장을 그대로 베끼고(취소한 대화에도 "주문을 잘 마쳤어요"), 복습 칸에 조언("Practice using 'a'…")이 들어가는 문제가 보였다. 대화 결과를 프롬프트에 넣고 예시 문장을 빼고 조언을 거르는 필터를 추가했더니(프롬프트 v3), 지표가 다시 떨어졌다.

| 버전 | precision | recall | F1 | 결과 파일 |
|---|---|---|---|---|
| v3 (요약·복습 수정) | 1.000 | 0.286 | 0.444 | `20261011-0631-feedback-prompt-v3.json` |

모델이 다시 문법 오류를 "어색한 표현"으로 분류했다("Can I has", "She want"). temperature 0.2에서 프롬프트가 조금만 바뀌어도 분류가 흔들렸다. 두 목록 중 하나를 고르게 하는 출력 구조가 근본 원인이라고 판단했다.

**개선 3: 한 줄씩 판정하는 출력 구조.** LLM이 고객 발화 한 줄마다 `grammar_ok`(참/거짓)를 반드시 판정하게 바꿨다. 문법이 틀린 줄은 문법 오류로, 문법이 맞고 어색한 줄만 어색한 표현으로 코드가 분류한다. 바뀐 것이 없는 수정(대소문자·문장부호만 다름)은 버린다. 사용자에게 보이는 `Feedback` 형식은 그대로다.

## EXP-ASR-001 Whisper 설정 비교 (합성 음성 기준선)

- 날짜: 2026-10-11 · 환경: RTX 4060 8GB, faster-whisper 1.1.0, `int8_float16` (GPU)
- 데이터: `evals/asr/script.txt` 30문장 × Kokoro 음성 4개(미국 남녀, 영국 남녀) × 조건 2개(깨끗함 / 합성 카페 소음 SNR 5dB) = 240개. 생성: `evals/asr/make_synthetic.py`
- **한계: 한국인 화자의 녹음이 아니다.** 실험 장치를 검증하고 설정 간 상대 비교를 하기 위한 기준선이다. 실제 녹음으로 다시 재야 한다(`evals/README.md` 녹음 가이드).

**문제.** 메뉴 단어가 포함된 주문 발화를 지연 예산(STT p95 ≤ 1.0초) 안에서 가장 정확하게 알아듣는 설정을 찾는다. 사전 등록한 채택 기준은 주문 정보 인식률 ≥ 95% 이면서 p95 ≤ 1.0초인 설정 중 가장 가벼운 것이다.

**결과**

| 조건 | 모델 | 문맥 힌트 | 토큰 제한 | WER | 주문 정보 인식률 | p50 / p95 (ms) |
|---|---|---|---|---|---|---|
| A | small.en | 없음 | 없음 | 0.054 | 0.892 | 242 / 349 |
| B | small.en | hotwords | 없음 | 0.109 | 0.904 | 255 / 4180 |
| C | large-v3-turbo | 없음 | 없음 | 0.031 | 0.888 | 306 / 508 |
| D | large-v3-turbo | hotwords | 없음 | 측정 못 함 (메모리 부족으로 프로세스 종료) | | |
| E | small.en | hotwords | 있음 | 측정 못 함 (메모리 부족으로 프로세스 종료) | | |
| F | small.en | 문장 프롬프트 | 있음 | 0.030 | 0.950 | 238 / 666 |
| G | small.en | 없음 | 있음 | 0.192 | 0.754 | 260 / 1330 |
| **H** | **small.en** | **문장 프롬프트** | **없음** | **0.030** | **0.950** | **236 / 349** |

조건별(H): 깨끗함 WER 0.008 · 인식률 0.983 / 소음 WER 0.053 · 인식률 0.917.

**원인 분석.**
- 힌트가 없으면(A, C) 메뉴 단어를 틀린다. 영국식 발음의 "hot"을 "heart"로, "oat milk"를 "oatmeal"로, "cold brew"를 "cold breath"로 인식했다. large 모델도 같은 실수를 했다.
- `hotwords`(B)는 그 실수를 고치지만, 힌트 단어 목록을 문장 끝에 그대로 덧붙이는 환각을 만들었다. 예: "Americano nonononono cold brew hot chocolate whole milk". WER이 두 배가 되고 긴 출력 때문에 p95가 4.2초로 늘었다.
- 출력 토큰 제한(G)은 단어 중간에서 문장을 잘랐다("hot lat"). 잘린 뒤 남은 구간을 다시 해석하면서 "Thanks for watching" 같은 환각이 생겨 가장 나빴다.
- 메뉴 단어를 넣은 자연스러운 문장을 `initial_prompt`로 주면(H) 메뉴 단어 오류가 줄었고 환각도 없었다.

**결정.** small.en + 문장 프롬프트, 토큰 제한 없음(H)을 기본값으로 정했다(`WHISPER_CONTEXT_MODE=prompt`). 채택 기준을 만족한다. large-v3-turbo는 WER은 비슷하게 낮지만 인식률이 낮고, 이 PC에서 Qwen3와 함께 올릴 메모리가 부족했다.

**다음 실험.**
- 실제 한국인 화자 녹음으로 H와 A를 다시 비교한다(EXP-ASR-001b).
- 메모리가 확보되면 D(large-v3-turbo + 문장 프롬프트)를 측정한다.
- Qwen3-ASR-0.6B 비교(EXP-ASR-002).

## EXP-ALIGN-001 wav2vec2 정렬로 멈춤 찾기

- 날짜: 2026-10-11 · 모델: wav2vec2-base-960h ONNX (Xenova 변환, 리비전 고정), numpy CTC 강제 정렬 (D-027)

**문제.** 대화가 끝난 뒤 "0.8초 이상 멈춘 곳"을 보여주려면 단어마다 시작·끝 시각이 필요하다. Whisper 단어 타임스탬프는 멈춤 앞뒤 단어의 경계가 흐리다.

**측정.** Kokoro로 만든 문장 가운데에 무음 1.2초(실제 모델 테스트는 1.5초)를 끼워 넣고 정렬했다.

| 항목 | 결과 |
|---|---|
| 끼워 넣은 1.2초 무음 | "hot" 앞 멈춤 1,246~1,366 ms로 검출 (자연스러운 단어 간격 포함) |
| 다른 단어 사이 멈춤 | 40~280 ms (긴 멈춤으로 오판 없음) |
| 처리 시간 (3.7초 문장) | CPU 약 220 ms, GPU 17~31 ms (첫 호출 제외) |
| 사용자 실제 음성 세션 (5문장) | 긴 멈춤 0건, 불확실 단어 구간 3개 표시 ("Iced Alon", "Yeah", "it") |

**결정.** 정렬은 대화 후에만 돌기 때문에 CPU로 충분하다. GPU 메모리는 실시간 모델에 남긴다. `pytest -m model`에 회귀 테스트를 넣었다.

**한계와 다음 실험.** 합성 음성과 사용자 한 명의 세션뿐이다. 한국인 화자 녹음으로 멈춤 검출의 정밀도·재현율을 사람 라벨과 비교해야 한다.

## EXP-HARNESS-001 평가 하네스로 같은 데이터 두 번 측정 (음성인식 힌트 없음 vs 문장 프롬프트)

- 날짜: 2026-10-11 · 커밋 `9a9097b` · 데이터: 대화 케이스 22개, 피드백 케이스 10개, 합성 음성 240개
- 결과 파일: `20261011-1516-suite-asr-plain.json`, `20261011-1520-suite-asr-prompt.json`
- 비교: `python ../evals/compare.py <두 파일>` 또는 웹 **평가 리포트** 탭

**목적.** `evals/run.py`가 기존 실험을 재현하는지, 한 가지 설정(음성인식 문맥 힌트)만 바꿨을 때 차이를 보여주는지 확인한다.

| 지표 | 힌트 없음 | 문장 프롬프트 (앱 기본값) |
|---|---|---|
| 음성인식 WER | 0.052 | **0.030** |
| 주문 정보 인식률 | 0.892 | **0.950** |
| 음성인식 p50 / p95 (ms) | 220 / 342 | 232 / 326 |
| 소음 조건 WER / 인식률 | 0.084 / 0.850 | 0.053 / 0.917 |
| NPC 장면 이탈률 | 10.8% | 7.2% |
| NPC 템플릿 대체율 | 8.4% | 4.8% |
| NPC 응답 p95 (ms) | 1,520 | 1,153 |
| 피드백 F1 / 잘못된 지적 비율 | 0.933 / 0.125 | 0.933 / 0.125 |
| 메뉴 환각률, 최종 가드 통과율, 행동 정확도 | 0%, 100%, 100% | 0%, 100%, 100% |

**해석.**
- 음성인식 수치는 EXP-ASR-001의 A(0.054 / 0.892)와 H(0.030 / 0.950)를 그대로 재현했다. 하네스가 같은 데이터로 같은 결과를 낸다.
- **NPC 지표 차이는 잡음이다.** 두 실행에서 LLM 설정은 같았다. 그런데도 장면 이탈률이 3.6%p, p95가 370 ms 달라졌다. 리포트가 "개선"으로 표시하더라도 이 정도 차이로는 결론을 내리면 안 된다. LLM 지표를 비교하려면 같은 설정으로 3회 이상 돌려 범위를 봐야 한다.
- 장면 이탈은 대부분 "3문장 이상"이었다. 문장 수 위반을 줄이는 프롬프트 실험이 다음 과제다.

**하네스 버그와 수정.** 첫 측정에서 힌트 없음 조건의 WER이 0.19로 나왔다. 원인은 `run_asr.evaluate()`의 출력 토큰 제한 기본값이었다. 예전 CLI에서 리팩터링하면서 앱과 반대로 켜져 있어, 실제로는 EXP-ASR-001의 G 조건을 잰 것이었다. 기본값을 앱과 같게(끔) 고치고 잘못된 결과 파일은 지웠다. 결과 파일에 `token_cap`도 기록한다.
